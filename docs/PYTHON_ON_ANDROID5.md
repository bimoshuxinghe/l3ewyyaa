# Python 爬虫在 Android 5 上的可行性调研

> 结论先行：**在 Android 5（API 21/22）上以库的形式、在宿主 App 内运行 Python + C 扩展，技术上不可行。**
> 本文件记录完整证据链，供后续决策参考。

## 1. 背景

本项目原使用 **Chaquopy 17.0.0** 提供 `.py` 爬虫支持，其 `minSdk` 硬性要求为 **24**。
目标是把 `minSdk` 降到 **21** 以支持 Android 5。

## 2. 实测证据（本项目内验证）

### 2.1 Chaquopy 插件层的限制

反编译 `com.chaquo.python:gradle:17.0.0` 的 `PythonPlugin.class`，`onVariant` 方法字节码：

```
7:   invokeinterface  Variant.getMinSdkVersion()
13:  invokeinterface  AndroidVersion.getApiLevel()
18:  bipush 24
20:  if_icmpge 77          // apiLevel < 24 -> 抛异常
23:  new  org/gradle/api/GradleException
...
55:  ldc "minSdk version 24 or higher"
```

即：`minSdk < 24` 时插件**在配置阶段直接抛 `GradleException`**，构建无法继续。

### 2.2 但这不是"仅插件层的限制"——底层有真实符号依赖

对 Chaquopy 实际产出的全部原生库做 `readelf` 符号扫描，结果：

```
[libpython3.10.so]      __register_atfork
[libchaquopy_java.so]   __register_atfork
[libcrypto_chaquopy.so] __register_atfork
[libssl_chaquopy.so]    __register_atfork
[libsqlite3_chaquopy.so]__register_atfork
[libc++_shared.so]      __cxa_thread_atexit_impl
[ujson.so]              __register_atfork
[Crypto/**/*.so]        __register_atfork   (全部 pycryptodome C 扩展)
[lxml etree.so 等]      __register_atfork
[bootstrap *.cpython-310.so] __register_atfork  (zlib/math/_ctypes/mmap/... 全部)
```

**Python 解释器本体与所有 C 扩展都依赖 `__register_atfork`。**

### 2.3 用 NDK 交叉验证符号的 API 可用性

以 NDK 28.2 自带的 `sysroot/usr/lib/arm-linux-androideabi/{api}/libc.so` 为准：

| 符号 | API 21 | API 22 | API 23 | API 24 |
|------|--------|--------|--------|--------|
| `__register_atfork` | ❌ 不存在 | ❌ 不存在 | ✅ | ✅ |
| `__cxa_thread_atexit_impl` | ❌ 不存在 | ❌ 不存在 | ✅ | ✅ |
| `mkostemp` | ❌ 不存在 | ❌ 不存在 | ✅ | ✅ |
| `__gnu_strerror_r` | ❌ 不存在 | ❌ 不存在 | ✅ | ✅ |

**bionic libc 在 API 21/22 根本没有导出这些符号**，因此依赖它们的 `.so` 在 Android 5 上 `dlopen` 必然失败：

```
java.lang.UnsatisfiedLinkError: dlopen failed:
  cannot locate symbol "__register_atfork" referenced by "libpython3.10.so"...
```

这不是配置问题，是 **libc 层面无法绕过的硬约束**。

## 3. 官方立场（chaquo/chaquopy issues）

### issue #718 —「Update minimum API level (2024)」

官方维护者 mhsmith 列出的 desupport 依据：

- **23**：Dynamic linker improvements（bionic 变更），可移除大量 importer workaround
- **24**：32-bit 大文件支持；**Java 8 default/static 方法问题**（#1204）；**扩展模块在 API 23 加载失败**（#1139）

### issue #1139 —「Extension modules fail to load on API level 23」

官方原文：

> This is a new problem with Chaquopy 15.0.1. It isn't present in 14.0.2, and the reason it
> was missed in 15.0.1 is because **we no longer do pre-release testing on API level 23** since
> we've abandoned TensorFlow.
>
> **We will desupport this API level in the next version of Chaquopy.**

报错：

```
com.chaquo.python.PyException: ImportError: dlopen failed:
  library "libpython3.8.so" not found
```

### issue #1204 —「Java 8 interface default/static methods can't be called from Python when minSdk < 24」

官方原文：

> For default methods, "desugaring" occurs to transform the bytecode into something which
> could have been generated by a Java 7 compiler. ... at runtime, the reflection API will
> indicate that the methods are abstract and not default. They can still be called via the
> subclass, but they can't be called via the interface.
>
> **No users have complained about this, and increasing `minSdk` is an easy workaround.**

Android 的 desugaring 机制会破坏 Python↔Java 桥的接口反射，这是**结构性限制**。

## 4. 替代方案评估

| 方案 | 能否在 Android 5 跑 Python 爬虫 | 原因 |
|------|------|------|
| **Chaquopy 17** | ❌ | 硬性 `minSdk >= 24` |
| **Chaquopy 15.0.1**（声称支持 API 21） | ❌ | 依赖 Gradle 9 已移除的 `org.gradle.util.VersionNumber`，构建直接崩；官方亦已在 API 23 实测崩溃并宣布放弃 |
| **GraalPy** | ❌ | 无官方 Android target/AAR；Truffle 依赖宿主 libc，无法运行于 bionic |
| **python-for-android** | ❌ | 是整套 App 脚手架，不能作为库嵌入宿主 App；且同样受 libc 符号限制 |
| **Termux** | ❌ | 需要自带 Linux userland，无法打包进 APK |
| **自编译 CPython（NDK --target=21）** | ⚠️ 理论可行但成本极高 | 需要重编 Python 解释器 + 全部依赖的 C 扩展（lxml/pycryptodome/ujson/…）并打补丁规避 atfork，工作量以人月计，且后续每次升级都要重来 |
| **把 Python 逻辑改为 JS/Java 实现** | ✅ | 与本项目现有 JS 爬虫/`csp_` Jar 爬虫能力重合，是最现实的路径 |

## 5. 对本项目的实际影响

同样的符号约束**不只影响 Python**，项目内其他原生库同样中招：

```
API23  libavcodec.so     __register_atfork      <- 软件解码核心
API23  libavformat.so    __register_atfork
API23  libavutil.so      __register_atfork
API23  libavfilter.so    __register_atfork
API23  libswscale.so     __register_atfork
API23  libswresample.so  __register_atfork
API23  libavdevice.so    __register_atfork
API23  libdav1d.so       __register_atfork      <- AV1 软解
API21  libc++_shared.so  __cxa_thread_atexit_impl
```

其中 ffmpeg 全家桶是 **ExoPlayer 软件解码（`decode=SOFT`）的依赖**。

受影响的还包括此前移除的库：
- `libmihomo.so` —— 声明 `minSdk=34`，低版本无法加载
- `libmpv.so` / `libplayer.so` —— 同为高 API target

## 6. 决策记录

| 目标组合 | 可行性 |
|----------|--------|
| Android 5 + 保留 Python 爬虫 | ❌ 不可能 |
| Android 5 + 保留 ffmpeg 软解 | ❌ 不可能 |
| Android 5 + 仅硬解（MediaCodec） | ✅ 可行 |
| minSdk 24 + 保留全部功能 | ✅ 可行 |

**最终选择**：维护 `minSdk = 21` 分支，移除 Chaquopy（Python 爬虫停用），**保留** ffmpeg
原生库——在 API 21-22 设备上由 media3 `LibraryLoader` 捕获 `UnsatisfiedLinkError`
优雅降级（软解不可用，回退硬解），在 API 23+ 设备上软解功能完全正常。

> media3 `LibraryLoader.isAvailable()` 已内建降级：
> ```java
> try { for (String lib : nativeLibraries) loadLibrary(lib); isAvailable = true; }
> catch (UnsatisfiedLinkError exception) { Log.w(TAG, "Failed to load " + ...); }
> return isAvailable;   // 返回 false，调用方走非软解路径
> ```
> 因此保留 ffmpeg 库**不会导致崩溃**，只是低版本设备上无法启用。

## 7. 内置直播源的 Java 化改造

移除 Chaquopy 后，原本由 Python 承载的**业务逻辑**必须补回来，否则内置直播源直接失效
（零配置默认源指向 `/ysp?list=live`，而 Python 侧那个 9979 HTTP 服务已随 Chaquopy 消失）。

| 原 Python 文件 | 行数 | Java 替代 |
|---|---|---|
| `live_ysp.py`（CKeyManager 加密引擎） | — | `live/cctv/CKeyManager.java` |
| `live_ysp.py`（频道表） | 73 条 | `live/cctv/YspChannels.java` |
| `live_ysp.py`（Spider 取流/缓存/测速） | 1045 | `live/cctv/YspSpider.java` |
| `live_ysp.py`（EPG 节目单，新增能力） | — | `live/cctv/YspEpg.java` |
| `migu_server.py`（MiguCore） | 680 | `live/migu/MiguCore.java` |
| `migu_server.py`（/ysp 路由 + 9980 绑定页） | — | `server/process/Ysp.java`、`server/process/Bind.java` |

关键设计约束：

1. **端口不能硬编码**。原 Python 版固定监听 9979（播放代理）与 9980（扫码绑定页）；
   现在统一挂在项目自带的 NanoHTTPD 上，端口由 `Server` 从 9978 起动态选取，
   所有回写给播放器的地址必须用 `Server.get().getAddress(true/false)` 实时拼接。
2. **列表必须是 M3U 格式**。`Live.catchup` 字段带 `@Ignore` 注解、永不从配置反序列化，
   catchup 只能逐频道从 `#EXTINF` 行的 `catchup=` / `catchup-source=` 属性获得
   （独立指令行如 `#EXT-X-CATCHUP:` 是无效的）。若改用 TXT 格式，回看功能会完全失效。
3. **回看参数拼接**：`catchup-type="append"` + `catchup-source="?playseek=${(b)yyyyMMddHHmmss}-${(e)yyyyMMddHHmmss}"`，
   `Catchup.append()` 发现原 URL 已带 query 时会把 `?` 换成 `&`，
   最终得到 `/ysp?fun=cctv&id=xxx&playseek=YYYYMMDDHHmmss-YYYYMMDDHHmmss`。
4. **切片相对路径必须用 URI 解析**，不能字符串拼接——相对路径可能含 `../`，绝对路径拼接会出双斜杠。
5. **回看依赖 EPG，`tvg-url` 不可省，且路径必须带 `.xml`**。`Catchup` 渲染 `playseek` 时取的是
   `EpgData.startTime/endTime`；若没有节目单，`EpgData` 的两个时间都是 0，
   会被渲染成 `19700101080000` 这个**格式合法但毫无意义**的时间戳。因此：
   - M3U 头必须带 `tvg-url="<base>/ysp?epg.xml"`，播放器据此拉节目单；
   - **后缀 `.xml` 是硬性要求**：`Live.getEpgXml()` 的过滤条件是
     `!url.contains("{") && (url.contains("xml") || url.contains("gz"))`，
     写成 `/ysp?epg` 会被静默忽略，回看照样失效（这个坑已实测复现）；
   - `YspSpider.handlePlayback()` 用 `MIN_PLAYBACK_TIMESTAMP` 兜底，
     识别出 1970 年时间戳时直接降级到直播，而不是把垃圾请求发给上游。

### EPG 实现要点（`YspEpg`）

上游：`https://api.cntv.cn/epg/epginfo3?serviceId=tvcctv&c=<code>&d=<yyyyMMdd>&cb=t`，
返回 JSONP，剥壳后每个频道形如 `{isLive, liveSt, channelName, program:[{t,st,et,showTime}]}`，
转换成 XMLTV 供 `EpgParser` 消费。

两个实测踩到的坑：

- **`cctv14` 被接口拒绝**，且**批量请求中只要有一个非法频道名，整批都返回
  `{"errcode":"1001","msg":"params error"}`**。因此 `epgCode()` 里维护了黑名单，
  同时 `fetchBatch()` 在整批失败后会自动逐个重试，让单个坏频道只影响它自己。
- **频道名不通用**：`cctv5p` 必须写成 `cctv5plus`；`cctv164k` 复用 `cctv16` 的节目单；
  `cctv9` 当天可能无节目；CGTN 系列与 4K/8K 超高清频道完全没有节目单。

算法移植采用**向量验证**（Python 生成参考向量 → JVM 断言相等）：

| 模块 | 覆盖内容 | 结果 |
|---|---|---|
| `CKeyManager` | TEA 加解密、xorArray、5 组 OISymmetry、ckey 往返 | 10/10 通过 |
| `MiguCore.ddCalcu` | 720p/登录两版、uid 各长度分支、pid 边界、sign 计算 | 148/148 通过 |
| `YspSpider` | 回看地址重写、CDN 替换、TS 绝对化 | 18/18 通过 |
| `YspEpg` | 真实接口拉取 → XMLTV → 时间格式 → 频道匹配 → 回看链路 | 16/17 频道、426 节目、852 时间戳全合法 |

回看链路的端到端验证（用真实节目时间）：

```
选中节目: 人口-2026-38    节目时间: 20260923003900 -> 20260923010100
最终 URL: http://127.0.0.1:9978/ysp?fun=cctv&id=cctv1&playseek=20260923003900-20260923010100
```
